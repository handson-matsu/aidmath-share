# 削除申請の重複防止・保存結果確認を公開GASへ追加する手順

今回の変更はローカル実装です。GAS・実シートへの反映、デプロイ、commit・pushは行っていません。**GASの更新を先に行い、その後フロントを公開してください。** 新フロントは照会機能を確認できなければ削除申請を送信しません。

## 調査結果と限界

従来のapp.jsは`requestDelete`へPOSTし、JSONの`ok:true`または`success:true`を成功と判定していました。POSTの90秒タイムアウト、通信/CORS障害、HTTP異常、JSON解析失敗、GASのエラー応答、成功フラグの欠落をすべて同じ文面で表示していました。

今回の「DeleteRequestsには保存済み」という報告から、保存は成功した一方、利用者画面が成功応答を確認できなかったことは分かります。しかし、実際の通信記録や当該時点のGASログがないため、タイムアウト・通信障害・応答形式のどれかは断定できません。テーマ取得の一時的な失敗も共通の通信問題の可能性はありますが、原因を確定する証拠ではありません。

ブラウザ側が通信を中断しても、GAS側の保存取消を要求する処理はありません。従来の削除申請はIDを送らず、再照会もせず、エラー後に再送できる構成でした。そのため保存済みの申請が重複する危険がありました。作品投稿にある重複防止・結果照会を削除申請にも追加しました。タイムアウト値を延ばす対応ではありません。

## 変更の範囲

- `app.js`：申請ID・理由・対象・送信者IDを送信前にlocalStorageへ保存。照会後に送信し、応答不明時は自動照会。再送も同じID。成功通知・送信済み控え・未確認の申請を開くボタン。
- `index.html`：削除ダイアログの保存結果確認ボタン・状態表示、ページ下部の未確認申請の入口。
- `style.css`：追加ボタンがスマートフォンで細く折り返されないよう、削除ダイアログ内を縦並びに調整。
- `gas/delete-requests.gs`：公開GASへ追加する専用処理。公開GASの完全版ではありません。
- テストと本手順書。管理者画面のコード・作品投稿GASは変更しません。
- 共通fetchは既存の成功判定・30秒GET/90秒POSTを維持。失敗の種類を安全な固定コードで区別し、削除申請の診断に利用します。他機能のエラー文は維持します。

## スプレッドシート

**列追加・移動は不要です。** DeleteRequestsは既存の以下7列をそのまま使用します。

|列|見出し|
|---|---|
|A|requestId|
|B|targetType|
|C|targetId|
|D|requesterId|
|E|reason|
|F|createdAt|
|G|status|

A列にクライアントの申請ID（`delete_`で始まる文字列）を保存します。新規G列は`pending`。管理画面の`approved`・`rejected`への更新と互換です。既存行は書き換えず、処理済みも含め全行でIDを照合します。既存行のIDを付け替えたり、重複防止のために行を削除したりしないでください。

対象検証にPostsのA〜I、CommentsのA〜Hの既存見出しも使用します。PostsのJ列requestIdには触れません。

## GASで手作業すること

1. 現在の**公開API用GAS**のコードとスプレッドシートをバックアップします。今回の追加先は管理専用GASではありません。
2. 公開GASに`delete-requests`というスクリプトファイルを追加し、このフォルダーの`delete-requests.gs`の全文をコピーします。既存の`getSheet(name)`を利用するため、その関数を残してください。新しいID・権限設定は不要です。
3. 既存の`doGet(e)`でactionを振り分けているswitchへ、次のcaseだけを追加します。既存の`topics`・`posts`・`comments`・`image`・`postStatus`はそのまま残します。

```javascript
case 'deleteRequestStatus':
  return jsonResponse(getDeleteRequestStatus(e.parameter));
```

4. 既存の`doPost(e)`でactionを振り分けているswitchへ、次のcaseだけを追加します。従来の`requestDelete`関数とcaseは残します。

```javascript
case 'requestDeleteV2':
  return jsonResponse(requestDeleteWithId(e.parameter));
```

5. 上記は、このプロジェクトの既存手順と同じ`jsonResponse`を使う書き方です。実際のGASが別名のJSON応答ヘルパーやswitch以外の構成なら、既存の方式に合わせてこの2つの分岐を追加してください。**doGet/doPost全体を置き換えないでください。** 呼び出し結果を`jsonResponse`に渡し、`return`することが必要です。
6. 同じ公開ウェブアプリの新バージョンとしてデプロイします。URL・実行ユーザー・公開範囲は維持してください。既存公開GASで追加の入力検証や頻度制限を共通処理として行っている場合、新actionにも適用されることを確認してください。
7. GAS更新後、ローカルの新フロントで下記を確認してから、GitHub Pagesへ新しい`app.js`・`index.html`・`style.css`を公開します。

新フロントは`requestDeleteV2`だけを送ります。旧画面との互換のため旧`requestDelete`を残しますが、**旧画面からの申請には今回の重複防止保証はありません**。更新後は利用者にページを再読み込みしてもらってください。

## 通信仕様

### GET `deleteRequestStatus`

パラメーター：`requestId`, `requesterId`

```json
{"ok":true,"protocol":"delete-request-v1","requestId":"delete_...","state":"saved"}
```

- `saved`：そのIDの行が保存済み。申請がpending・approved・rejectedのどれであっても保存済みです。
- `processing`：ロックを取得できず処理待ち。その申請自体の実行中を証明する値ではありません。
- `not_found`：照会時点で行がない。遅れて到着する送信まで否定するものではありません。

申請理由や管理状態、内部IDを応答に追加しません。requesterIdも照合しますが、匿名IDはGoogleログイン認証ではありません。

### POST `requestDeleteV2`

従来と同じフォーム形式で`requestId`, `requesterId`, `targetType`, `targetId`, `reason`を送ります。

保存済みなら上と同じ`saved`応答。ロック待ちは`processing`。対象の存在と公開状態、理由の長さなどを検証してから、DeleteRequestsに1行だけ追加します。理由の先頭が`=`の入力はシートの数式化を避けるため拒否します。

同じIDで対象・理由・送信者が異なる場合は拒否します。保存済みの行を先に確認するため、その後対象がhidden/deletedになっても保存結果を確認できます。

## 再送・保存情報の扱い

- 同じブラウザ匿名ID・対象種別・対象ID・理由からSHA-256で同じ申請IDを作ります。同じ内容を2タブで同時に送っても同じIDになり、GASのScriptLock内で重複確認と保存を行います。
- 送信前に保存した理由は変更せず、再送時も同じ値を使います。再読み込み後も照会・同じ申請の再送ができます。保存機能が利用できなければ送信しません。
- 成功後も送信済みの控えを残し、同じ対象のダイアログを開き直して新しい申請を作ることを防ぎます。この画面には送信済み対象への新しい申請を作る機能はありません。新たな事情がある場合は管理者に相談してください。
- localStorageには申請理由も残ります。共有端末ではブラウザを共有する人が同じ匿名ID・保存情報を使います。本文・画像は追加保存しません。
- ブラウザの保存データを消すと匿名IDが変わり、新しい申請として扱われます。別端末も同様です。未確認の間は保存データを消さないでください。
- **今回の修正前に送った申請のIDは新画面では分かりません。今回報告された保存済み申請を再送せず、管理者画面で確認してください。** 既存行と新IDを推測で対応づける移行処理はありません。
- 同じ公開GAS内のScriptLockは作品投稿とも共有されます。画像保存などが長い場合、申請は処理待ちになることがあります。
- 管理専用GAS・シートの手動編集とはロックを共有しません。申請ID・対象・理由を書き換えたり、行を物理削除したりしない運用が必要です。

## 実環境での確認手順

1. GASの2つのactionを追加して新バージョンを公開します。ブラウザは最新画面へ再読み込みします。
2. テスト用コメントから理由を入力して削除申請します。「削除申請を送信しました。管理者が確認します。」が表示されることを確認します。
3. DeleteRequestsに1行だけ追加され、A列が`delete_...`、G列が`pending`であることを確認します。
4. 同じ対象の削除申請を再度開き、「送信済み」と表示されて新規送信できないことを確認します。
5. 通信結果不明になった場合は「保存結果を確認する」を使います。ページを再読み込みしても、下部の「未確認の削除申請を確認する」から照会を続けられます。対象が既に公開画面から消えていても、この入口を使えます。
6. 未保存で同じ申請を再送する場合は、IDを作り直さず「同じ申請を再確認・再送する」を使います。行が増殖しないことを確認します。応答喪失やタイムアウトを本番で無理に再現する必要はなく、これらは模擬テストでも確認しています。
7. 管理者画面で申請を承認し、コメントdeleted・申請approved・公開画面から非表示になることを確認します。別のテスト申請を却下した場合は対象の状態が変わらないことも確認します。
8. テーマ・作品・画像表示、作品投稿、コメント・返信、管理者のテーマ管理が従来どおり動くことを確認します。

エラーが続く場合は発生時刻と画面の「確認情報」を記録してください。`timeout`は設定時間内に応答全体を読めなかったこと、`network`はfetch失敗、`http`はHTTP異常、`json`は本文の読取・解析失敗、`api`はGAS側のエラー応答、`unconfirmed`は成功フラグ不足、`protocol`は照会・応答仕様の不一致です。これだけで通信障害の根本原因までは断定できません。GAS実行ログとブラウザのNetworkを照合し、Cookieや内部IDなどを公開しないようにしてください。

## ローカルテストとpush前チェック

```sh
node tests/delete-requests-gas.cjs
node tests/delete-requests-browser.cjs
node tests/post-requests-gas.cjs
node tests/post-requests-browser.cjs
node tests/smoke.cjs
node admin-gas/tests/topics.cjs
node admin-gas/tests/moderation.cjs
node admin-gas/tests/browser.cjs
node admin-gas/tests/moderation-browser.cjs
```

ブラウザテストにはPlaywrightとChromeが必要です。別パスのPlaywrightを使う場合はNODE_PATHを指定します。新規テストは実GASに接続しません。HTTPエラー・JSON不正・成功フラグ欠落・保存後応答喪失・タイムアウト・未保存再送・再読み込み・照会不能・旧GAS・連打・2タブ送信・保存領域利用不可を模擬します。GASテストはロック競合・同じIDの再送・保存後例外・所有者照合・既存列・処理済み申請・対象検証を確認します。

push前に、GAS側の先行反映と実環境の基本確認、差分に個人情報・管理IDがないこと、公開GAS完全版や管理画面を意図せず変更していないことを確認してください。GitHubへpushしてもGASは自動更新されません。
