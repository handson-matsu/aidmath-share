# AidMath-Share 管理専用GAS

このフォルダーは、公開APIとは別の**管理専用GASプロジェクト**へコピーするコードです。テーマ・作品・コメント・削除申請を管理します。今回のコード変更では実シートの変更、GASへの反映・デプロイ、GitHubへのcommit・pushは行っていません。

## 実装内容

- テーマ管理：全テーマの一覧、追加、テーマ名・説明の編集、公開／非公開。新規は画像・コメント有効、非公開。既存の`tiling`は変更不可。画像・コメント有効フラグは表示・保持のみ。
- 作品管理：全状態の作品を新しい順に表示。テーマ名・投稿者・タイトル・本文・投稿日・状態を確認し、公開／非公開・論理削除を操作。
- コメント管理：登録順の降順で50件ずつ表示。コメント状態・親作品状態で絞り込み、公開／非公開・論理削除を操作。親作品が公開中でないコメントの再公開は拒否。
- 削除申請管理：最初はpendingだけを表示。「すべて」で処理済みも確認。対象内容と理由を見て承認・却下。
- 作品・コメントは`published → hidden`、`hidden → published`、`published / hidden → deleted`。deletedから戻す機能はありません。
- 承認は対象をdeletedにした後、申請をapprovedにします。却下は申請のみrejectedにし、対象を変更しません。処理済み申請は再処理できません。
- 行削除や画像ファイル削除は行いません。本文もシートに残ります。親コメント・作品の状態を変えても、関連コメントのstatusは変更しません。
- 対象が存在しない・対象種別や状態が不明な申請は承認できません。pendingであれば却下できます。申請自体が不明なstatusの場合は処理できません。

利用者側は、公開APIがpublishedだけを返す既存仕様を利用します。公開フロントと公開GASの変更は不要です。非公開作品へのコメントも、コメント自身がpublishedであっても既存公開APIの作品チェックにより表示されません。テーマ非公開はテーマ一覧からの非表示であり、作品そのもののstatus変更とは異なります。

## スプレッドシートの列構成

**既存の列追加・移動は不要です。** 以下の先頭列の見出しと順序を検証し、不一致・空ID・重複IDがあればその処理を停止します。自動移行・行削除・並べ替えはしません。完全な空行は読み飛ばします。

|シート|A列から順番の見出し|管理機能による更新|
|---|---|---|
|Topics|topicId, title, description, imageEnabled, commentEnabled, isActive|既存機能どおり|
|Posts|postId, topicId, authorId, displayName, title, body, imageFileId, createdAt, status|I列statusのみ|
|Comments|commentId, postId, authorId, displayName, body, replyTo, createdAt, status|H列statusのみ|
|DeleteRequests|requestId, targetType, targetId, requesterId, reason, createdAt, status|G列statusのみ|

PostsのJ列requestIdとそれ以降、CommentsのI列以降、DeleteRequestsのH列以降は読み書きしません。既存の投稿requestId重複防止情報を保持します。

TopicsのD〜Fは文字列ではなく真偽値を前提とします。Posts/Commentsのstatusはpublished・hidden・deleted、DeleteRequestsはpending・approved・rejectedです。不明な状態は一覧に明示し、作品・コメントの状態変更や申請処理を拒否します。自動的に公開状態へ置き換えません。

## 管理者がGASで行う手順

### 既に管理専用プロジェクトがある場合

1. 現在の管理用GASコードとスプレッドシートをバックアップしてください。最初はシートをコピーして、テスト用の管理GASを接続すると実データを変更せず確認できます。
2. **公開APIではなく、既存の管理専用GASプロジェクト**を開きます。
3. 次の4つのスクリプトファイルを追加し、同名ファイルの内容をコピーします：`ModerationService`、`PostsService`、`CommentsService`、`DeleteRequestsService`。GASエディターでは拡張子.gsが付きます。
4. 既存のHTMLファイル`Index`、`App`、`Styles`を今回の内容へ置き換えます。同じ関数を別ファイルへ重複してコピーしないでください。
5. `Config.gs`、`Main.gs`、`TopicsService.gs`、`appsscript.json`は既存のものを維持します。今回、新たな権限の追加はありません。Drive権限は不要です。
6. スクリプトプロパティの`SPREADSHEET_ID`が対象シートを指し、`ADMIN_EMAIL`が管理者本人のGoogleアカウントであることを確認します。IDやメールをソースへ直接書かないでください。
7. シートの見出しを上の表と照合します。`adminListPosts`・`adminListComments`・`adminListDeleteRequests`は読み取り専用なので、エディターから実行してエラーがないことを確認できます。
8. 管理用GASの「デプロイ」→「デプロイを管理」→編集→バージョン「新バージョン」で更新します。実行ユーザーは**自分**、アクセスできるユーザーは**自分のみ**を維持してください。公開APIのデプロイには触れません。
9. 管理URLを再読み込みし、以下の動作確認を行います。

コードを保存するだけでは既存の/exec URLに新しいコードが反映されないため、新バージョンへの更新が必要です。GitHubへのpushもGASの更新にはなりません。

### 初めて管理専用プロジェクトを作る場合

1. 管理者のGoogleアカウントで新しい独立したGASプロジェクトを作成します。
2. 上表の7つの.gsファイルと3つのHTMLファイルをコピーします。HTML名は`Index`・`App`・`Styles`です。
3. プロジェクト設定からマニフェストを表示し、このフォルダーの`appsscript.json`の内容を設定します。
4. スクリプトプロパティに`SPREADSHEET_ID`と`ADMIN_EMAIL`を設定します。
5. 管理者が対象シートを編集できることを確認し、`adminListTopics`を実行して必要な権限を承認します。
6. ウェブアプリとして、実行ユーザー「自分」・アクセス「自分のみ」で新規デプロイします。

画面表示と各RPCでassertAdmin_を通し、アクセス中ユーザーと実行ユーザーがADMIN_EMAILに一致することを確認します。取得できない場合も拒否します。認証チェックを削除して回避しないでください。管理画面をGitHub Pagesで配信する構成ではありません。

## 動作確認の手順

テスト用シートで最初に確認してください。論理削除も実際の公開表示に影響します。

1. **認証**：管理者で画面が開くこと、別アカウント・未ログインでは利用できないこと。
2. **テーマ管理の維持**：既存tilingが保護されていること。別のテストテーマで追加・編集・公開／非公開を確認。画像・コメントフラグと既存の追加列を保持すること。
3. **作品管理**：テーマ名・本文などを確認。テスト作品を非公開→再公開と操作し、PostsのI列だけが変わること。削除の確認ダイアログでキャンセルすると変わらないこと、確定するとdeletedになり、再公開ボタンが出ないこと。J列requestIdと画像IDも維持されること。
4. **コメント管理**：通常コメントと返信を確認。非公開→再公開→削除を確認。親だけを非公開・削除しても返信のH列statusが変わらないこと。
5. **申請管理**：pendingだけが初期表示されること。対象種別・本文・理由を確認。作品とコメントの申請をそれぞれ承認し、対象deleted・申請approvedになること。却下では申請rejectedになり対象が変わらないこと。「すべて」で処理済みを確認し、操作ボタンがないこと。
6. **同時操作**：同じ申請を2つのタブで開いて一方を処理し、古いタブからの再処理が拒否されること。作品・コメントの古い画面からの上書きも拒否されること。
7. **公開側**：再読み込み後、hidden/deletedの作品・コメントが表示されず、再公開したものが表示されること。非公開作品のコメントは表示されないこと。非公開・削除済み親コメントへの新規返信は既存公開GASによって拒否されること。
8. **表示**：スマートフォン幅で4メニュー・本文・操作ボタンが使えること。処理中・成功・失敗のメッセージを確認。
9. **データ保持**：行数、本文、作者ID、返信先、作成日時、追加列が保持されること。Drive画像は削除されません。

## 二重処理・通信エラーと運用上の制約

- ボタンの連打を抑止し、同じ管理GASプロジェクト内の更新をScriptLockで直列化します。処理済み申請は拒否します。
- 更新対象は行番号を画面から受け取らず、保存時にIDから再検索します。既存の内容から作ったrevisionを照合し、古い内容の上書きを拒否します。
- スクリプトロックは公開GASやシートの手動編集とは共有されません。管理操作中は対象シートの直接編集・行の並べ替え・別の管理GASからの更新を避けてください。
- 承認は2つのシートを更新するため、一括で成功／取消するトランザクションではありません。**対象をdeletedにして保存後、申請をapprovedにします。** 中断すると「対象deleted・申請pending」が残ることがあります。
- この場合は一覧を再読み込みして内容を確認し、同じpending申請を再承認してください。既にdeletedの対象は再更新せず、申請の承認を完了します。対象本文が取得後に変更されていたら再取得を要求します。別の申請ですでにdeletedになった同じ対象へのpending申請も、内容を確認して承認できます。
- エラー時に自動で元の公開状態へ戻すことはしません。承認途中で対象deletedになった後に却下しても、対象はdeletedのままです。「却下」は対象の復元操作ではありません。
- 通信結果不明時はボタンを消して再読み込みを案内します。エラー表示だけで保存失敗と判断しないでください。
- 作品・削除申請の一覧取得は従来どおりです。コメント管理は以下のページ分割方式です。作品・コメントには画像プレビューを付けず、本文で対象確認します。

## ローカルテスト

Node.jsで以下を実行します。ブラウザテストにはPlaywrightとChromeが必要です。Playwrightが別パスの場合はNODE_PATHを指定してください。

```sh
node admin-gas/tests/topics.cjs
node admin-gas/tests/moderation.cjs
node admin-gas/tests/browser.cjs
node admin-gas/tests/moderation-browser.cjs
node admin-gas/tests/comments-pagination.cjs
node admin-gas/tests/comments-browser.cjs
```

- topics：既存テーマ管理の認証、追加、フラグ保持、tiling保護、更新競合など。
- moderation：認証、列検証、不明状態の拒否、ID再検索、状態列だけの更新、返信保持、承認／却下、二重処理防止、途中失敗からの再承認。
- browser：既存テーマ画面の回帰確認。
- moderation-browser：模擬シートと実サービスコードを使った画面切り替え・状態操作・確認キャンセル・連打・通信エラー・スマートフォン幅の確認。

テストは実GAS・実シートには書き込みません。Googleの実認証、デプロイ設定、実サービスの制約、公開APIとの連動は、実環境で別途確認が必要です。

## コメント管理のページ分割（2026-10-01）

### 実データの事前確認

管理者のブラウザーから既存AidMath-Share-Dataを読み取り専用でxlsxにエクスポートし、Commentsの行番号・ID・createdAtを確認しました。データは2〜13行目の12件。途中の空行、空ID、重複ID、日時不正、下の行で日時が古くなる逆転はありませんでした。行順を登録順として扱ううえで支障は見つかりませんでした。過去の手動操作履歴を証明するものではありません。実データ・シート・GASの編集は行っていません。実データのコピーはリポジトリへ含めません。

### 取得・表示仕様

- 登録順＝Commentsの行番号降順。日時による並べ替えはしません。運用上、行の並べ替え・物理削除はしないでください。
- 初期は最新50件。コメント状態はすべて／公開／非公開／削除済み、親作品状態はすべて／公開中／非公開／削除済み／作品不明。両方の初期値はすべてです。
- 作品不明には親作品の不存在・空ID・未知のstatusを含みます。重複した親作品IDは曖昧な対象としてエラーにします。
- `adminListComments({status, postStatus, snapshotRow, startRow})` は `{items, snapshotRow, startRow, nextRow}` を返します。itemsは最大50件です。引数省略時も全件ではなく最新50件です。管理画面とCommentsServiceは同時に反映してください。
- 最初に最終行を固定し、その範囲内を100行ずつA〜H列で読みます。50件一致するか先頭に達するまで、1回のGAS実行内で走査します。時間・走査行数による中断やブラウザーからの継続検索はありません。
- PostsはA列のTextFinder完全一致検索で対象行を特定し、E〜I列の1行だけ読みます。同一RPC内のMapで同じ作品の再検索を避けます。永続キャッシュ・索引用シートはありません。
- フィルターが疎な場合や一致なしの場合は、結果として全Commentsを分割走査する場合があります。PostsのID検索も索引検索の速度保証はありません。GAS実行時間超過等ではエラーを表示し、不完全な結果を最終結果として表示しません。
- 次へは最後の確認行の直前から、前へはブラウザーに保存したページ開始位置から取得します。保持するのは現在の最大50件と開始位置の履歴です。全コメントの転送・描画はしません。
- 未走査行が残っていれば次へを有効にします。残りに一致がなければ現在ページを維持し、それ以降に該当データがない旨を表示します。
- フィルター変更と「再読み込み」は条件を維持して最新の先頭ページへ戻ります。新規投稿はこの時点で取り込みます。通常の次／前の移動中は最初に固定した最終行より新しい追加行を含めません。
- コメント更新後は条件とページ開始位置を維持して再取得します。条件から外れた行は古い行で補充し、後続のページ履歴は作り直します。ページが空なら前へ戻ります。他タブからの状態変更までは固定しません。
- コメント再公開時はサーバー側でも親作品がpublishedであることを再確認します。親がhidden／deleted／不明なら拒否。閲覧・非公開化・論理削除は可能です。コメント自身がdeletedの場合は従来どおり変更不可です。
- 状態更新はコメントIDを完全一致検索し、対象行のrevision確認後、H列だけを更新します。画面からの行番号を更新先として信用しません。管理GAS内のScriptLockを維持します。
- 一覧取得のID検証は走査した範囲が対象です。取得ごとの全シート重複監査は行いません。更新対象IDと参照作品IDは検索結果の重複を拒否します。

### ローカル検証と反映対象

10,003件の模擬コメントで全20フィルターの全ページを走査し、順序・最大50件・重複／取りこぼしなし・前ページの再取得を検証。初期の条件なし取得はComments100行だけ、Postsの値取得は対象1行ずつであることを検証しています。希少条件で1,000行を超えても同一RPC内で先頭まで検索すること、閲覧中の追加、空シート、不正カーソル、更新競合、親作品変更直後の再公開拒否も検証します。

画面テストも10,003件の模擬シートを使用し、全20フィルター、次／前、フィルター変更時のリセット、状態変更後の2ページ目維持・50件補充、空ページ時の前ページ復帰、再公開ボタン制限、通信エラーからの復帰、スマートフォン幅を確認します。

今回の反映対象は管理専用GASの `CommentsService.gs`、`App.html`、`Index.html` です。既存公開GAS・生徒用フロント・シート列構成の変更は不要です。今回はローカル実装・模擬検証のみで、実環境への反映・デプロイ・Pushはしていません。
